Summary for engineering management

MITRE's 2025 eCTF insecure example is a small MAX78000 decoder firmware plus host-side Python tooling, released by MITRE under Apache-2.0. In the code that is actually in the repository nothing blocks distribution: there is no GPL, LGPL or AGPL code, and the Maxim startup file that ScanCode marks as 'proprietary' is a permissive MIT-style licence. The open items are about what the repository does not contain: the ADI MSDK is downloaded and linked at build time and was not scanned, there is no third-party notices file or SBOM for the firmware, and the optional wolfSSL crypto example would statically link GPL code into the firmware if anyone turns it on.

Key risks

  • Turning on the eCTF Crypto Example (CRYPTO_EXAMPLE=1) compiles wolfSSL (GPL-3.0-or-later unless you buy a commercial licence) into the firmware image. That would become a Red: copyleft over the whole image, plus GPLv3 installation information on a locked-boot device.
  • The ADI MSDK v2024_02 libraries linked into the firmware are downloaded at build time and were not scanned, so their licences and notices are not confirmed.
  • No third-party notices file ships with the firmware, although Apache-2.0 (MITRE code, and probably the MSDK) and the Maxim MIT-style startup licence both require notices to go with binary distributions.
  • Every source file says it is 'provided only for educational purposes for the 2025 MITRE eCTF competition'. Anyone reusing the code commercially should record how that statement relates to the Apache-2.0 grant.

What is working well

  • A single, clear project licence: Apache-2.0 in LICENSE.txt, with MITRE's public-release approval (Case 24-03351-Code).
  • Consistent MITRE copyright headers on every first-party source file.
  • GPL wolfSSL is kept out of the repository (gitignored), and the crypto example that uses it is off by default.
  • Third-party Maxim files keep their original copyright and licence headers intact.
  • The build environment is defined in a Dockerfile, so the toolchain and SDK version (MSDK v2024_02) can be identified and audited.

What's wrong

The reference design includes an optional 'eCTF Crypto Example' (simple_crypto.c/.h) built on wolfCrypt. It is off by default (CRYPTO_EXAMPLE=0), and wolfSSL is not in the repository: the README tells developers to download it into decoder/wolfssl/, and .gitignore excludes that directory. If it is turned on, the Makefile adds wolfssl/wolfcrypt/src to VPATH, and MSDK auto-search compiles those sources straight into the single statically linked MAX78000 image. wolfSSL is dual-licensed: GPL-3.0-or-later for current releases (GPL-2.0-or-later before 5.6.6), or a commercial licence from wolfSSL Inc.

Field impact

In the default build: no exposure. With the crypto example on under the GPL option, distributing the firmware would mean offering the complete corresponding source of the whole image (MITRE code, MSDK and wolfSSL) under GPL-3.0. On a device that only boots signed or packaged images, GPL-3.0 section 6 also requires the Installation Information needed to install modified firmware. Either of these would make this a Red.

Recommendation

Decide this now and record it. Either (a) keep CRYPTO_EXAMPLE=0 and enforce it, for example a CI check that fails if decoder/wolfssl/ exists or CRYPTO_EXAMPLE=1 in a release build; or (b) buy a wolfSSL commercial licence before enabling it; or (c) use a permissive crypto library instead, such as Mbed TLS / TF-PSA-Crypto (Apache-2.0), Monocypher (BSD-2-Clause or CC0) or tinycrypt (BSD-3-Clause), or the MAX78000's hardware AES/TRNG drivers from the MSDK.

What's wrong

The firmware links CMSIS device startup/system files, the MAX78000 peripheral drivers (flc, icc, uart, nvic_table, mxc_delay) and the FTHR_RevA board support package (LIB_BOARD and LIB_PERIPHDRIVERS are on by default), all from the Analog Devices MSDK. The Dockerfile fetches the MSDK at build time, so none of it is in the repository and neither scanner could check it. Most MSDK files are expected to be Apache-2.0, with some older Maxim MIT-style headers and Arm's Apache-2.0 CMSIS. Vendor SDKs can also carry use-with-vendor-silicon terms. That condition would be met here (the target is ADI's own MAX78000), but it has not been confirmed.

Field impact

The largest third-party part of the shipped image has unconfirmed licences and attributions. If any linked MSDK file is under a more restrictive or vendor-only licence, that is not known. Apache-2.0 §4 notice obligations for the MSDK are not being met at the moment (see OSS-003).

What's wrong

All 26 MITRE-authored source files carry this statement and a MITRE copyright line, but no licence identifier. The root LICENSE.txt grants Apache-2.0 with 'Approved for Public Release; Distribution Unlimited', so read in context the statement is most likely a quality and warranty disclaimer, not an extra licence condition. Read on its own, though, 'provided only for educational purposes' can be taken as a field-of-use restriction, and no file states which governs.

Field impact

For the eCTF competition itself: none. For anyone reusing this code in a commercial product: an unresolved question about whether non-educational use is permitted. That needs a recorded position before the code ships outside the competition.

What's wrong

The firmware image (max78000.bin / .elf) combines MITRE Apache-2.0 code, the Maxim MIT-style startup file, the MSDK (probably Apache-2.0) and newlib-nano (BSD-style per-file notices). The repository has no NOTICE file, no THIRD_PARTY_NOTICES file and no documented place where these notices go with the binary. LICENSE.txt covers only the MITRE code.

Field impact

Distributing the binary without these notices does not meet Apache-2.0 §4(a) (give recipients a copy of the licence), the Maxim licence condition (the copyright notice and permission notice must be included in all copies or substantial portions) or newlib's BSD-style attribution conditions. This is easy to fix, but it is an obligation.

OSS-005AMBERNo SBOM, and the build pulls the SDK and base image by mutable referenceSBOM & compliance processdecoder/Dockerfile:5
Confidence: confirmedEffort: MEU CRA Annex I Part II (1) SBOMCycloneDX 1.5

What's wrong

There is no SBOM and no compliance process in the repository. The build image tracks the moving ubuntu:24.04 tag and installs unpinned apt packages, including the toolchain that supplies newlib and libgcc. The MSDK zip is fetched with no checksum, and the Python dependencies are unpinned with no lockfile. So the exact third-party content of a given firmware build cannot be reproduced or listed afterwards.

Field impact

Release-by-release notices and SBOMs cannot be shown to be accurate. Under the EU Cyber Resilience Act, a manufacturer placing a product like this on the EU market must keep an SBOM of at least its top-level dependencies.

What's wrong

GCC, binutils, gdb, make, libtool and texinfo (GPL family) run only inside the build container and never ship. What reaches the image from the toolchain is libgcc (GPL-3.0-or-later WITH GCC-exception-3.1) and newlib-nano (mostly BSD-style). The exception allows linking libgcc into proprietary firmware, and newlib only needs attribution. The container image is not distributed to device recipients.

Field impact

No copyleft obligation on the firmware from the toolchain, provided the build container itself is not handed to customers or contract manufacturers. If it is, that is distribution of GPL programs, and the source-offer obligations apply.

No change needed. Add the newlib and libgcc licence texts to the notices (OSS-003). If the Docker image is ever given to third parties, provide the Ubuntu source packages or a written offer.
