Summary for engineering management

This is MITRE's deliberately insecure reference decoder for the 2025 eCTF: a MAX78000 firmware that receives subscription updates and broadcast TV frames from a host over UART and returns the frame contents for subscribed channels. As expected for an intentionally insecure example, it is not fit for field release: the UART packet parser lets a single oversized or undersized message corrupt or leak stack memory, and the content-protection model has no cryptography at all, so subscriptions can be forged, expired subscriptions never lapse, and frames are broadcast in cleartext. Robustness gaps (no watchdog, non-atomic flash updates, ignored host ACK failures, printf in an interrupt handler) would cause hangs and lost state in the field.

Key risks

  • Any UART/broadcast message longer than 100 bytes overwrites the main loop's stack buffer (memory corruption, crash, possible code execution).
  • A decode message shorter than 12 bytes makes the decoder stream ~64 KB of RAM beyond its buffer back to the host before faulting.
  • Subscription updates are accepted from anyone, for any decoder ID, with no signature or MAC: subscriptions can be forged.
  • Frames are cleartext and unauthenticated, and timestamps are ignored: anyone on the broadcast sees every channel, expired subscriptions keep working, and old or forged frames are accepted.
  • No watchdog and spin-forever fault handlers: once the decoder faults it stays hung until power-cycled.

What is working well

  • Wire structures are explicitly packed (#pragma pack) and match the host's struct.pack layouts, so the protocol layout itself is unambiguous.
  • The emergency channel (0) cannot be overwritten by a subscription update, and list_channels() is bounded by MAX_CHANNEL_COUNT, so the list response cannot overflow.
  • Persistent state lives in a dedicated flash page (second to last page) outside the application image, and a first-boot canary initialises it to a known state.
  • The build is containerised (Dockerfile) with the MSDK pinned to the v2024_02 release tag, and -Wall is enabled.
  • The wolfSSL crypto example, which uses an all-zero key, is compiled out of the default build.

FW-001REDUART packet length (up to 65,535) copied into 100-byte stack buffer without a bounds checkMemory safetydecoder/src/host_messaging.c:197
Confidence: confirmedEffort: SCWE-121CWE-787CWE-20ETSI EN 303 645 5.13EU CRA Annex I

What's wrong

read_packet() takes the 16-bit length straight from the message header and passes it to read_bytes(), which writes that many bytes into the caller's buffer. The only caller passes main()'s 100-byte stack array, and neither function knows or checks the buffer size. Frames reach this path verbatim from the satellite broadcast (tools/ectf25/tv forwards the received bytes unchanged), so the length is controlled by whoever can inject into the broadcast or talk to the UART.

Field impact

Any message with a body over 100 bytes overwrites main()'s other locals, saved registers and the top of the stack (the stack sits at the end of SRAM). The mild outcome is a crash that hangs the decoder until power-cycle (see FW-010); the severe one is attacker-influenced corruption of control data, giving code execution on the decoder and access to everything it holds. One malformed frame in the broadcast could take down every decoder listening.

What's wrong

decode() subtracts the 12-byte header (channel + timestamp) from pkt_len without first checking pkt_len >= 12, and stores the result in a uint16_t. A shorter packet wraps to 65,524-65,535. FW-009AMBERFlash page erased on every subscription message with no rate limit or change checkHardware, storage & powerdecoder/src/decoder.c:243
Confidence: likelyEffort: SCWE-400CWE-1246

What's wrong

Each accepted subscription update, including one identical to what is already stored, erases and rewrites the same flash page. Because updates are unauthenticated (FW-003), the host side can issue them as fast as the UART allows. On-chip flash is rated for a finite number of erase cycles per page (check the MAX78000 data sheet for the exact figure; it is in the order of ten thousand).

Field impact

A misbehaving or malicious host loop can wear out the status page within hours of continuous updates, after which subscriptions can no longer be stored reliably and the decoder may lose its configuration on every boot. Normal use is unlikely to reach the limit, which is why this is Amber.

Two builds of the same commit can use different compilers and SDK content, so a field issue may not be reproducible, and a tampered download would go unnoticed. Regulators under the CRA will expect an SBOM.

Pin the base image by digest, pin gcc-arm-none-eabi and other packages to versions, verify the MSDK zip with a sha256sum, and generate an SBOM (for example with syft) as part of the release build.

FW-016AMBERNo firmware version, reset-reason reporting or crash recordField readiness & diagnosticsdecoder/src/decoder.c:373
Confidence: confirmedEffort: SETSI EN 303 645 5.10NIST IR 8425EU CRA Annex I

What's wrong

The image embeds no version or build ID and no command returns one; the reset reason is never read; there is no crash record across reboot (see FW-010). The hotspot scan found no version definition, reset-reason or fault-handler code in first-party sources.

Field impact

When decoders misbehave in the field, support cannot tell which firmware they run or why they rebooted, so fixes cannot be targeted or confirmed.

Recommendation

Embed a version string and git hash at build time, expose them through a host command, read and report the MAX78000 reset cause at boot, and add the .noinit crash record from FW-010.

FW-017AMBERRegulatory process items not evidenced: disclosure policy, support period, SBOM, provisioningRegulatory complianceREADME.md
Confidence: needs-verificationEffort: MUK PSTIETSI EN 303 645 5.2EU CRA Annex I Part II

What's wrong

The repository contains no SECURITY.md or vulnerability disclosure contact, no stated security support period, no SBOM step and no per-device provisioning procedure. These are required by the EU CRA, UK PSTI and ETSI EN 303 645 for consumer connected products. This is engineering guidance, not legal advice; the compliance owner should confirm which regimes apply to the product and their current dates.

Field impact

Without them the product cannot be placed on the EU or UK market once those obligations apply, regardless of code quality.

Recommendation

Publish a vulnerability disclosure policy and contact, state the support period, add SBOM generation to the release build (FW-015), and document per-device key provisioning and debug lock at manufacturing (FW-014). Close each item with a link to the evidence.

FW-018AMBERNo unit tests for the packet parser and only -Wall in the buildCode quality & styledecoder/Makefile:252

What's wrong

The UART parser and command handlers have no host-side unit or fuzz tests, and the build does not use -Wextra, -Wsign-compare or -Wconversion, which would have flagged FW-002 and FW-006. The tools/ testers exercise the happy path through hardware only.

Length and signedness defects like FW-001, FW-002 and FW-006 go unnoticed until they fail in the field.

Compile host_messaging.c and the decode/subscribe handlers on the host against a fake UART and fuzz read_packet() with libFuzzer or AFL; add -Wextra -Wconversion -Wsign-compare and run cppcheck/semgrep in CI.

FW-020GREENCrypto example (compiled out) uses an all-zero AES key, raw ECB blocks and MD5Securitydecoder/src/simple_crypto.c:51
Confidence: confirmedEffort: SCWE-327CWE-328CWE-1204

What's wrong

The optional wolfSSL example encrypts each 16-byte block independently (ECB), with no IV or authentication, demonstrates it with an all-zero key, and offers MD5 as the hash. It is disabled in the default build (CRYPTO_EXAMPLE=0), which is why this is Green.

Field impact

None in the shipped build. If a team enables it as the basis of FW-004's fix, frames would leak patterns and be forgeable, which would be Red.

FW-021GREENFirst-boot initialisation writes uninitialised channel IDs to flashCode quality & styledecoder/src/decoder.c:306
Confidence: confirmedEffort: SCWE-457

What's wrong

The id field (and struct padding) of each default slot is never set, so stack garbage is persisted to flash. Every reader also checks active, so the garbage is never acted on today.

Field impact

No current field impact; makes flash contents non-deterministic and could matter if a future change reads id without active.

Evidence

    subscription[i].start_timestamp = DEFAULT_CHANNEL_TIMESTAMP;
    subscription[i].end_timestamp = DEFAULT_CHANNEL_TIMESTAMP;
    subscription[i].active = false;
}

Recommendation

Zero the array first (memset or = {0}) before setting the defaults.

Recommended next steps

  1. Fix the two parser Reds (FW-001, FW-002) first: they are small, local changes and make every other test meaningful.
  2. Design the content-protection scheme as one piece of work: authenticated, encrypted frames with per-channel keys (FW-004), signed decoder-specific subscriptions (FW-003), and timestamp window and monotonic checks (FW-005).
  3. Add a watchdog, real fault handlers with a crash record, and A/B flash storage (FW-010, FW-008).
  4. Add host-side unit and fuzz tests for read_packet() and the command handlers, plus -Wextra and cppcheck/semgrep in CI (FW-018).
  5. Obtain the bootloader and confirm image signing, rollback protection and debug lock (FW-013, FW-014); generate a compile_commands.json with 'bear -- make' so clang-tidy can run next time.
